# AI Agent 题 — 完整记录

> 这道题要求：领养一只 Coding Agent → 让它读我的 Git 仓库 → 交给它一个小任务 → 用 `git diff` 看它改了什么 → 把过程记下来。
> 下面就是我的真实过程（所有命令输出都是本机实际跑出来的）。

---

## 任务 1：我的使用记录

### 1.1 我用了什么 Agent

**Hermes Agent**（Nous Research 出的开源 CLI Agent）。

- 运行环境：Windows 11 + WSL2（Ubuntu），Agent 本体装在 WSL 里（`~/.hermes/`）。
- 模型：`deepseek-v4-flash`（provider: `deepseek`），在 `~/.hermes/config.yaml` 里配置。
- 为什么选它：它同时具备“读文件 / 改文件 / 执行终端命令 / 搜索项目”这几类工具，
  而且能在项目里放规则文件（本题提到的“员工手册”），正好用来做题。

### 1.2 安装和配置过程

1. 安装：按官方安装脚本装到 WSL（安装器会准备好 Python 环境、虚拟环境和 `hermes` 命令）。
2. 选模型：`hermes model` 里挑 provider 和模型（我用的 DeepSeek）。
3. 确认状态：`hermes doctor` 检查环境，`hermes` 直接进入对话。
4. 配项目规则：在仓库根目录放一个 `AGENTS.md`（见本仓库），写上“这个仓库是干什么的、
   文件怎么放、改完要检查什么、什么不能动”。
5. 验证工具权限：让它跑 `git status`、列目录，确认它真的能操作这个仓库，而不是只在聊天框里空谈。

> 我的理解：安装本身没什么难点，**难点在于“给它立规矩”**——不写规则文件它就像新员工一样乱放文件、乱改内容。

### 1.3 我交给它的任务

**第一步（只读）**：在这个仓库里问它

> 阅读当前仓库，不要修改任何东西。简单介绍一下这个仓库中有什么。

它的回答（摘）：这是一个只有 Markdown 文档的学习笔记仓库，根目录有 `README.md`（仓库用途）、
`git-notes.md`（Git 学习笔记）、`AGENTS.md`（Agent 规则）、`AI_USAGE.md`（AI 使用说明），
`notes/` 目录用于专题笔记；目前**没有任何代码**，也没有 `.env`、密钥文件。

**第二步（小任务）**：让它做两件事

> 1）在 `README.md` 里补一小节，说明“AI 使用说明在哪个文件、仓库里不允许出现密钥”；
> 2）按 `AGENTS.md` 的约定，新建 `notes/ai-agent-notes.md` 并写入 AI agent 题的记录。

### 1.4 Agent 做了哪些修改

- **新建** `notes/ai-agent-notes.md`（就是本文件）；
- **修改** `README.md`：在末尾增加一节「AI 使用与规则」，指向 `AGENTS.md` 和 `AI_USAGE.md`，
  并写明“仓库里不允许提交密钥”。

### 1.5 `git diff` 里我看到了什么

关键点：**`git diff` 默认不显示“还没被 Git 跟踪的新文件”**。新建文件要先标记一下才看得到内容：

```bash
git status                        # 看到 README.md 被修改、notes/ai-agent-notes.md 是 untracked
git add -N notes/ai-agent-notes.md   # -N = intent-to-add，只登记不暂存内容
git diff --stat
git diff README.md                # 只看 README 的改动
```

`git diff README.md` 的真实输出（完整）：

```diff
diff --git a/README.md b/README.md
index 283bab2..10e2439 100644
--- a/README.md
+++ b/README.md
@@ -37,3 +37,9 @@ git add <文件>
 git commit -m "说明这次改了什么"
 git push
 ```
+
+## AI 使用与规则
+
+- 本仓库的 AI 协助说明见 [`AI_USAGE.md`](AI_USAGE.md)。
+- 给 AI Agent 的项目规则见 [`AGENTS.md`](AGENTS.md)。
+- 仓库里**不允许**出现密码、Token、API Key 等敏感信息。
```

`git diff --stat` 的统计：

```text
 README.md               |   6 ++
 notes/ai-agent-notes.md | 183 ++++++++++++++++++++++++++++++++++++++++++++++++
 2 files changed, 189 insertions(+)
```

看到的两件事：

1. 改动范围**只有** `README.md` 一处追加 + 一个新文件，没有动 `git-notes.md`、没有重排格式——
   说明 `AGENTS.md` 里写的“优先最小改动、不要重写整个文件”真的被遵守了。
2. diff 里没有出现任何密钥、临时文件，符合“不提交敏感信息”的要求。

### 1.6 结果是否符合预期

基本符合，两处小偏差：

- 它一开始把新文件写成 `ai-agent-notes.md`（放在根目录），和 `AGENTS.md` 里“笔记放 `notes/`”冲突；
  我指出来之后它移动到了 `notes/`。→ 说明**规则文件写了也要看它有没有真的执行**，需要人来复核。
- 它起草的第一次 README 补充写得太长（半屏）。我要求“只补一小节”，它才收敛。

**结论**：Agent 完全可以完成这类“读仓库 + 小改动 + 写文档”的工作，但
“检查它是否遵守了规则、改动是否最小”这件事必须由我来做。

## 任务 2：五个问题的回答

### 1. Agent 为什么能读取文件、修改代码，而普通聊天 AI 通常不能？

因为 **Agent 多了一层“工具（Tool）+ 执行循环”**，而聊天 AI 只有“输入文本 → 输出文本”。

- 聊天 AI 的输出只是文字，它自己**没有**你电脑的访问权限，也没法知道文件里到底有什么；
  它说“请把 xxx 改成 yyy”，动手的还是你。
- Agent 背后同样是大语言模型，但模型可以**决定调用工具**：读文件、写文件、执行命令、搜索代码……
  工具在**你的电脑上**真的被执行，结果再作为新信息返回给模型，模型据此继续下一步。

一句话：聊天 AI 的回答是“建议”，Agent 的动作是“真的改了文件”——差别不在模型，而在**有没有工具和权限**。

### 2. Tool 在 Agent 中起到了什么作用？

Tool 是 Agent 与外部世界之间的**接口**，它把“模型的意图”变成“真实的副作用”：

- **获取信息**：读文件、搜索、查看目录、（在本题里）看 `git diff`——模型看不到这些，只能通过 Tool 问。
- **产生改动**：写文件、执行命令、提交代码——这些是聊天 AI 做不到的。
- **形成闭环**：模型调用工具 → 工具返回结果 → 模型根据**真实结果**决定下一步（而不是凭想象往下写）。
  这正是它能“跑测试、看报错、再改”的原因。

本题里这一点特别直观：如果 Agent 没有 `git diff` 这个工具，它就无从确认自己改了什么、改得对不对。

### 3. 为什么项目需要给 Agent 配置一份类似“员工手册”的规则？

因为 Agent 第一次进入你的项目时，**对项目一无所知**：不知道仓库是干什么的、文件放哪、用什么风格、
改完要不要测试、哪些东西不能碰。没有规则时它会“自由发挥”——把笔记放到根目录、顺手重排整个文件、
甚至把 `.env` 一起提交上去。

规则文件（`CLAUDE.md` / `AGENTS.md` / `.hermes.md`）解决三件事：

1. **省去每次重复解释**：“这个仓库只放 Markdown 笔记”说一次就够。
2. **约束行为边界**：能改什么、不能改什么、什么绝对不能提交（密钥）。
3. **统一产出风格**：目录结构、命名、提交信息格式，让多人/多 Agent 协作的结果保持一致。

而且它是**可版本管理的文档**：规则被改错了，`git diff` 能看到、能回滚。

### 4. Agent 为什么可能“忘记”之前说过的内容？额度是怎么算的？

**“忘记”的原因**：大模型没有记忆，它每次只能看到**当前上下文窗口（context window）**内的内容。
对话太长、代码太长、工具返回太多，超出窗口后最早的内容就会被压缩或丢弃，于是出现
“我刚刚不是说过吗”。长对话里“早期约定被丢掉”是常态，不是它故意装傻。

**额度怎么算**：两笔账。

- **token 账**：模型按 token（词元，可粗略理解为“词/字片段”）计费或限制，**输入和输出都算**。
  一次问答的消耗 = 系统提示 + 全部历史对话 + 项目文件内容 + 工具返回结果 + 模型输出的 token，
  所以“同一句话问第二遍”比第一遍贵（历史更长了）。
- **额度账**：产品层面还有限制——按分钟/天的请求数（RPM/TPM）、上下文长度上限、
  订阅套餐的用量池，用完就报“额度不足”，要等窗口重置或升级。

实用结论：**重要约定要写进规则文件（文件不占对话上下文、可随时重新读取），长任务要开新会话，
并且别把一整个大项目塞进一次对话。**

### 5. 如果一个 Agent 可以随便执行任何终端命令，会有什么风险？

风险和“给你电脑一个不受限制的远程操作员”是一样的：

- **不可逆的数据损失**：`rm -rf`、清空分支、覆盖同名文件——命令一旦执行，很多操作无法撤销。
- **凭据泄露**：读走 `~/.ssh`、`.env`、Token，或者把密钥提交到公开仓库（推到公网就删不掉历史了）。
- **供应链/下载执行风险**：从网上拉一段脚本直接执行、装来历不明的包。
- **越权与外部副作用**：用你的身份发消息、改线上数据、产生真实费用（调用付费 API、开机器）。
- **“看起来很对”的错误**：Agent 会自信地跑错命令（比如 `pkill -f worker-` 把不想杀的进程一起杀掉）。

所以合理的做法是：**最小权限、危险操作要先确认、关键步骤先 `git diff`/先备份、把密钥放进环境变量
而不是文件、重要仓库用分支而不是直接推 main**。本题 `AGENTS.md` 第 5 节的“禁止事项”就是这个思路。

## 任务 3（可选）：Skill / MCP 这类东西

我实际接触到的是**两层扩展**：

1. **Skill（技能包）**：把“做某类任务的标准流程”写成可复用的 Markdown（例如“如何排查 fetch 失败的网页”
   “如何提交一次 PR”），Agent 遇到对应场景时自动加载。它解决的是“**动作怎么做得对**”的问题——
   比每次口头交代更稳定。我的理解：Skill 约等于团队里沉淀的 SOP 文档。
2. **MCP（Model Context Protocol）**：把外部系统（数据库、GitHub、浏览器、公司内部服务）
   以统一协议暴露成工具给 Agent 调用。它解决的是“**能碰哪些系统**”的问题——Tool 的扩展插座。

再加上**记忆（memory）**：跨会话保存稳定事实（我是谁、环境是什么、约定是什么），
与 Skill（流程）分工明确：**记忆记事实，Skill 记流程**。

> 我的体会：Agent 的“能力上限”很大程度上不是模型的智力，而是**给它接了多少工具、写了多少规则**。
